# Environments and Installers

## What

**Virtual environments** isolate a project's dependencies from the system
Python and from other projects. **`pip`** is the standard package
installer. **`uv`** is a modern, fast, Rust-based installer/resolver/
project manager that covers venv creation, dependency resolution, and
locking in one tool.

## Why

Backend projects depend on specific, pinned versions of many packages
(FastAPI, SQLAlchemy, etc.). Without isolation, installing one project's
dependencies can silently break another's, or clash with the system
Python. Reproducible environments are a prerequisite for CI, Docker builds,
and onboarding a new engineer without "works on my machine" problems.

## How

### `venv` — isolation

```bash
python -m venv .venv
source .venv/bin/activate      # macOS/Linux
.venv\Scripts\activate          # Windows

python -m pip install fastapi
deactivate
```

`venv` creates a directory with its own Python interpreter symlink and
`site-packages`, so `pip install` only affects that environment. Every
Python project should run inside a virtual environment — installing
dependencies into the system Python is a common source of conflicts and is
difficult to reproduce or clean up.

### `pip` — installing packages

```bash
pip install fastapi==0.115.0
pip install -r requirements.txt
pip freeze > requirements.txt   # snapshot exact installed versions
pip list --outdated
pip uninstall fastapi
```

`pip` reads a `requirements.txt` (or `pyproject.toml`, in modern usage) and
installs packages plus their dependencies. `pip freeze` captures exact
versions for reproducibility, but doesn't distinguish direct dependencies
from transitive ones — a known limitation addressed by lockfile-based
tools (see `uv` below and
[pyproject.toml and Dependency Management](02-pyproject-and-dependency-management.md)).

### `uv` — fast, integrated tooling

```bash
uv venv                          # create a virtual environment
uv add fastapi                   # add a dependency, updates pyproject.toml + uv.lock
uv add --dev pytest              # add a dev-only dependency
uv sync                          # install exactly what's in uv.lock
uv run pytest                    # run a command inside the project's environment
uv lock                          # regenerate the lockfile
```

`uv` combines what previously required several tools (`venv`, `pip`,
`pip-tools`/`poetry` for locking) into one fast binary. It manages
`pyproject.toml` and a `uv.lock` lockfile together, so `uv sync` reproduces
an environment exactly across machines/CI, unlike a loose
`requirements.txt`.

### Comparing the three

| Tool | Role | Lockfile | Speed |
|---|---|---|---|
| `venv` | Environment isolation only | No | N/A |
| `pip` | Package installer | No (needs `pip-tools`/manual freeze) | Baseline |
| `uv` | Env + installer + resolver + lockfile | Yes (`uv.lock`) | Significantly faster (Rust-based resolver) |

## When to use

- Always work inside a virtual environment (`venv` or one `uv`
  manages implicitly) — never install project dependencies into the
  system/global Python.
- Use `pip` directly for simple scripts or when a project's tooling
  hasn't adopted anything more integrated.
- Use `uv` for new projects needing fast, reproducible installs and a real
  lockfile without stitching together multiple tools.

## When NOT to use

- Don't install packages with `sudo pip install` or into the system
  Python — this can break OS tooling that depends on a specific system
  Python setup (especially on Linux).
- Don't rely on `pip freeze > requirements.txt` as your only
  reproducibility mechanism for anything beyond a small script — it
  doesn't distinguish direct from transitive dependencies, making
  intentional upgrades harder to reason about.
- Don't mix `pip install` and `uv` dependency management inconsistently in
  the same project — pick one workflow so `pyproject.toml`/lockfile stay
  authoritative.

## Common mistakes

- Forgetting to activate the virtual environment before installing
  packages, polluting the system Python instead.
- Committing a virtual environment directory (`.venv/`) to version control
  instead of `.gitignore`-ing it and relying on the lockfile to recreate
  it.
- Treating `requirements.txt` generated by `pip freeze` as a source of
  truth for *direct* dependencies — it mixes in every transitive
  dependency, making it unclear what the project actually declared as a
  requirement versus what pip resolved underneath.
- Not pinning versions at all (`pip install fastapi`) in a way that's
  reproduced later — without a lockfile, re-running the same install
  command later can resolve different transitive versions.

## Interview questions

1. Why does every Python project need a virtual environment?

   **Answer:** Without one, every project shares the same global
   `site-packages`, so two projects needing different versions of the same
   library will stomp on each other. A venv gives each project its own
   isolated interpreter + package directory.

   ```bash
   python -m venv .venv
   source .venv/bin/activate
   ```

2. What's the difference between `pip freeze` output and a real lockfile?

   **Answer:** `pip freeze` just dumps whatever happens to be installed
   right now — it can't tell you which packages were direct dependencies
   vs pulled in transitively. A real lockfile (`uv.lock`) is generated by
   a resolver, tracks the dependency graph, and is meant to be
   regenerated deterministically, not hand-edited.

3. What problem does `uv` solve that `pip` + `venv` alone don't?

   **Answer:** `uv` bundles env creation, installing, resolving, and
   locking into one fast tool, so you don't need to stitch together
   `venv` + `pip` + `pip-tools`/`poetry` yourself — and its resolver is
   dramatically faster, which matters at CI scale.

4. What happens if you install packages without activating a virtual
   environment?

   **Answer:** `pip install` falls back to the system/global Python,
   polluting it with project-specific packages that can conflict with
   other tools on the machine (or require `sudo` and risk breaking OS
   tooling on Linux).

5. How would you reproduce an exact set of dependency versions across
   machines/CI?

   **Answer:** Commit a lockfile (`uv.lock`) alongside `pyproject.toml`,
   and have CI/every machine install *from* the lockfile (`uv sync`)
   rather than re-resolving ranges fresh each time.

## Senior-level considerations

- Reproducibility (lockfiles, pinned versions) is a prerequisite for
  reliable CI/CD and Docker builds — an unpinned dependency tree is a
  common source of "it worked yesterday, broke today" incidents. For
  example, a Dockerfile doing `pip install fastapi` (no version, no
  lockfile) can pull a different, breaking release on every rebuild.
- Tool choice (pip vs uv vs poetry) is a team-level decision that affects
  onboarding speed and CI cache-ability — `uv`'s speed matters
  meaningfully at CI scale (faster installs = faster pipelines). A CI job
  that took 90s with `pip install -r requirements.txt` can often drop to a
  few seconds with `uv sync` and a warm cache.
- In containerized deployments (see
  [Images, Containers, and Dockerfiles](../devops/docker/01-images-containers-and-dockerfiles.md)),
  the same
  environment/dependency principles apply — a Dockerfile should install
  from a lockfile, not float on unpinned `pip install` calls, to keep
  builds reproducible across rebuilds. For example, `COPY uv.lock
  pyproject.toml . && uv sync --frozen` fails the build loudly if the
  lockfile and pyproject drift apart, instead of silently installing
  something different.
